# 작업 목록: <기능 이름>

**입력**: `docs/spec/<NNN-기능-이름>/`의 설계 문서

**선행 조건**: plan.md (필수), spec.md (사용자 스토리에 필수), research.md, docs/design/db.md, docs/design/api.md

**테스트**: 아래 예시에는 테스트 작업이 들어 있다. 테스트는 선택 사항이며, 기능 명세에서 명시적으로 요청했을 때만 넣는다.

**구성**: 사용자 스토리별로 작업을 묶어서 스토리마다 독립적으로 구현하고 테스트할 수 있게 한다.

## 형식: `[ID] [P?] [스토리] 설명`

- **[P]**: 병렬로 할 수 있음 (다른 파일, 의존성 없음)
- **[스토리]**: 이 작업이 속한 사용자 스토리 (예: US1, US2, US3)
- 설명에 정확한 파일 경로를 쓴다

## 경로 규칙

- **단일 프로젝트**: 레포 루트의 `src/`, `tests/`
- **웹 앱**: `backend/src/`, `frontend/src/`
- **모바일**: `api/src/`, `ios/src/` 또는 `android/src/`
- 아래 경로는 단일 프로젝트를 가정한다. plan.md의 구조에 맞게 바꾼다

## 의존성과 실행 순서

### 단계 의존성

- **준비 (Phase 1)**: 의존성 없음 - 바로 시작할 수 있다
- **기반 (Phase 2)**: 준비가 끝나야 한다 - 모든 사용자 스토리를 막는다
- **사용자 스토리 (Phase 3+)**: 모두 기반 단계가 끝나야 한다
  - 그 뒤에는 사용자 스토리를 병렬로 진행할 수 있다 (인력이 있으면)
  - 또는 우선순위 순서대로 차례로 진행한다 (P1 → P2 → P3)
- **다듬기 (마지막 단계)**: 원하는 사용자 스토리가 모두 끝나야 한다

### 사용자 스토리 의존성

- **사용자 스토리 1 (P1)**: 기반 (Phase 2) 뒤에 시작할 수 있다 - 다른 스토리에 의존하지 않는다
- **사용자 스토리 2 (P2)**: 기반 (Phase 2) 뒤에 시작할 수 있다 - US1과 통합할 수 있지만 독립적으로 테스트할 수 있어야 한다
- **사용자 스토리 3 (P3)**: 기반 (Phase 2) 뒤에 시작할 수 있다 - US1/US2와 통합할 수 있지만 독립적으로 테스트할 수 있어야 한다

### 각 사용자 스토리 안에서

- 테스트가 있으면 구현 전에 먼저 쓰고 실패해야 한다
- 모델 다음에 서비스
- 서비스 다음에 엔드포인트
- 핵심 구현 다음에 통합
- 스토리를 끝낸 뒤 다음 우선순위로 넘어간다

### 병렬 기회

- [P] 표시된 준비 작업은 모두 병렬로 할 수 있다
- [P] 표시된 기반 작업은 모두 병렬로 할 수 있다 (Phase 2 안에서)
- 기반 단계가 끝나면 모든 사용자 스토리를 병렬로 시작할 수 있다 (팀 여력이 있으면)
- 한 사용자 스토리의 [P] 표시 테스트는 모두 병렬로 할 수 있다
- 한 스토리 안의 [P] 표시 모델은 병렬로 할 수 있다
- 서로 다른 사용자 스토리를 다른 팀원이 병렬로 맡을 수 있다

## 구현 전략

### MVP 먼저 (사용자 스토리 1만)

1. Phase 1: 준비 끝내기
2. Phase 2: 기반 끝내기 (중요 - 모든 스토리를 막음)
3. Phase 3: 사용자 스토리 1 끝내기
4. **멈추고 확인**: 사용자 스토리 1을 독립적으로 테스트
5. 준비되면 배포/시연

### 점진적 전달

1. 준비 + 기반 끝내기 → 기반 준비 완료
2. 사용자 스토리 1 추가 → 독립 테스트 → 배포/시연 (MVP!)
3. 사용자 스토리 2 추가 → 독립 테스트 → 배포/시연
4. 사용자 스토리 3 추가 → 독립 테스트 → 배포/시연
5. 각 스토리가 이전 스토리를 깨지 않고 가치를 더한다

### 병렬 팀 전략

개발자가 여럿일 때:

1. 팀이 함께 준비 + 기반을 끝낸다
2. 기반이 끝나면:
   - 개발자 A: 사용자 스토리 1
   - 개발자 B: 사용자 스토리 2
   - 개발자 C: 사용자 스토리 3
3. 스토리가 각각 끝나고 독립적으로 통합된다

## 참고

- [P] 작업 = 다른 파일, 의존성 없음
- [스토리] 라벨은 추적을 위해 작업을 특정 사용자 스토리에 연결한다
- 각 사용자 스토리는 독립적으로 끝내고 테스트할 수 있어야 한다
- 구현 전에 테스트가 실패하는지 확인한다
- 작업 하나나 논리적 묶음마다 커밋한다
- 어느 체크포인트에서든 멈춰서 스토리를 독립적으로 확인할 수 있다
- 피할 것: 모호한 작업, 같은 파일 충돌, 독립성을 깨는 스토리 간 의존성
