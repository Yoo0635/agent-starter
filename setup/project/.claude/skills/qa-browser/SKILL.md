# 알파 화면 QA (ego 브라우저)

요청: $ARGUMENTS

## 고정값

- 대상: cafe24 알파 `https://workbench.ultari.co.kr`. 계정은 yoo0635.
- 로그인은 사용자가 한다. 비밀번호는 입력하지 않는다. 로그인 화면(`/login`)이 나오면 `task.handOff()` 로 넘기고 멈춘다.
- 브라우저: ego 브라우저만 쓴다. 시작할 때 `ego-browser skill` 을 실행해 안내를 따른다. Git Bash heredoc 으로 스크립트를 넘긴다.
- Space: 도메인마다 하나, 이름은 `qa-<도메인>`. `taskSpace("qa-<도메인>")` 로 이어 쓴다.
- ego 창은 최소화하지 않는다(최소화되면 스크린샷이 실패한다).

## 대상 시나리오

- `docs/spec/<도메인>/*/spec.md` 의 시나리오(`^[0-9]+\. \*\*Given\*\*`)와 성공 기준(`^- \*\*SC-[0-9]+\*\*`). spec 번호순으로 본다.
- common, test 도메인은 대상이 아니다.

## 판정 기준과 미리 거르기

이 스킬은 화면 층만 본다. 내부(DB·이벤트·권한 경로·시간·장애)는 백엔드 시험과 qa-full 이 맡는다. 기준은 하나다: **yoo0635 혼자, 화면이나 `/api/v1` 으로 결과를 직접 볼 수 있는가.**

spec 을 시작하면 브라우저를 열기 전에 항목마다 셋 중 하나로 나눠 `요약.md` 에 적는다. **본다**만 실제로 누른다.
- **본다**: 화면에 보이거나 `/api/v1` 응답으로 확인된다. 필요한 데이터는 직접 만들 수 있다.
- **화면에서 확인 불가**: DB·outbox·투영·코드 구조·`/internal` 을 봐야 하거나, 다른 사용자 로그인·서버 시계 조작·장애 주입·두 DB 방언 비교·동시 경합이 필요하다. 이유 한 줄과 함께 적고 건너뛴다.
- **수동**: 하면 내 로그인이 끊기거나, 실제 사람에게 알림이 가거나, 목데이터·남의 데이터가 망가진다(아래 "하지 않는 조작"). 이유 한 줄과 함께 적고 건너뛴다.

## 한 시나리오 확인

1. 화면에서 직접 누른다: `snapshot` → `click`·`fill` → `waitForSelector`/`waitForFunction` → 다시 `snapshot`.
2. 화면만으로 판정이 안 되면 같은 페이지에서 `page.evaluate` 안의 `fetch("/api/v1/...")` 로 응답을 대조한다. 화면이 실제로 부르는 주소는 `performance.getEntriesByType("resource")` 로 찾는다.
   - 쓰기 요청(POST·PUT 등)은 처음에 403 `CSRF_INVALID` 가 나는 게 정상이다. 그 응답으로 `XSRF-TOKEN` 쿠키가 생기니 `document.cookie` 에서 읽어 `X-XSRF-TOKEN` 헤더에 싣고 한 번 더 보낸다(화면도 이렇게 한다). 이 403 은 실패가 아니다.
   - 접근 토큰은 몇 분이면 끝난다. 직접 부른 API 가 401 이면 `page.reload()` 로 화면이 토큰을 갱신하게 한 뒤 다시 부른다.
3. **본다**로 고른 항목의 판정은 셋 중 하나로 적는다(미리 거른 확인 불가·수동과 합쳐 다섯 가지).
   - **통과**
   - **실패**: 기대와 실제, 근거(스크린샷 경로나 API 응답 요약). 실패로 적기 전에 같은 단계로 한 번 더 재현한다. 두 번째에 통과하면 실패가 아니라 "불안정"으로 기록 파일에 적는다. 재현할 때 단계마다 스크린샷을 `docs/qa/<도메인>/img/QA-<도메인>-NNN-<단계>.png` 로 남기고, QA 파일에서 상대 경로로 보여 준다. QA 파일과 함께 커밋한다.
   - **판정 불가**: 데이터를 만들어 봐도 조건을 맞출 수 없음
4. 조건에 맞는 데이터가 없으면 화면에서 직접 만들어서 본다. 만든 데이터는 이름·제목 앞에 `[QA-<실행 접두어>]` 를 붙인다(실행 접두어는 도메인을 시작할 때 `MMDDHHmm` 으로 정해 `요약.md` 에 적는다). QA 가 끝나도 지우지 않는다.
5. 화면을 열 때마다 `page.evaluate` 로 `window.fetch` 를 감싸 응답 상태를 모으고 `window.addEventListener("error")`·`"unhandledrejection"` 으로 JS 오류를 모은다. 시나리오가 끝나면 모은 것을 읽는다. 4xx·5xx 응답과 JS 오류가 있으면 시나리오 판정과 별도로 실패 파일을 쓴다. 쓰기 요청의 첫 403 `CSRF_INVALID` 와 토큰 만료 401 은 빼고 본다.
6. yoo0635 는 SYS_ADMIN 과 EXEC 를 가진 최고 권한 계정이다(`GET /api/v1/me` 의 `isSysAdmin`·`isExec`). 권한이 모자라 403 이 나면 그 권한을 더 붙인다. 낡은 입력 때문에 나는 403(`*_STALE`)은 권한 문제가 아니므로 실패로 적는다.

## 하지 않는 조작

어기면 밤새 멈추거나 남에게 피해가 간다. 이것이 필요한 항목은 **수동**이다.

1. **내 로그인 끊기**: 로그아웃, `/auth/login` 이동, yoo0635 대상 모든 기기 로그아웃(`revoke-tokens`), 토큰 회수, 비서 토큰 발급·폐기, yoo0635 자신의 권한 지정·회수. SYS_ADMIN 은 누구에게도 지정·회수하지 않는다.
2. **조직 동기화 수동 실행**: 메신저 조직도에 없는 `mock_` 사용자가 모두 비활성이 된다(identity/012).
3. **실제 사람에게 알림**: 일 부탁·떠넘기기·멘션·담당·참여자·문의 담당의 대상은 yoo0635 자신이나 `mock_` 사용자만. 쓰기 직전에 대상 userId 를 확인한다.
4. **남의 데이터 쓰기**: 쓰기(취소·수정·담당 변경·기록·멘션)는 이번 실행의 `[QA-<접두어>]` 데이터에만 한다. 그 밖의 데이터는 읽기만 한다.
5. **계약 만료 임박 날짜**: 계약 끝나는 날은 과거나 2030년 이후로만 잡는다(만료 알림이 실제 사람에게 간다).
6. **실제 부서로 담당 부서 변경**: 고객 담당 부서는 `mock_` 부서로만 바꾼다.
7. **대량·병렬 요청**: 병렬 20~50건 같은 시나리오는 순차 3건 이내로 줄여 본다. 틀린 비밀번호 시험은 없는 아이디로 1번만 한다.
8. **긴 대기**: 토큰 만료·1시간 max-age·방해 금지 시간대처럼 기다려야 하는 항목은 기다리지 않는다(확인 불가).

뒷정리(도메인 끝에 한다):
- `mock_` 사용자에게 지정한 권한은 회수한다.
- 수락할 사람이 없어 남은 떠넘기기는 yoo0635 가 취소한다.
- 알림 설정은 시작 전에 `GET /api/v1/me/notification-prefs` 로 저장해 두고 끝에 되돌린다. 방해 금지는 켜지 않는다.
- 개수를 세는 시나리오는 `q=[QA-<접두어>]` 처럼 이번 실행 접두어로 걸러서 센다(할 일·고객은 지울 수 없어 쌓인다).
- 알림 목록이 403 STALE 이면 notification/003 은 "환경 차단"으로 한 번 적고 반복 시도하지 않는다.

## 한 번에 한 도메인

- Space 는 한 번에 하나만 연다. 다른 도메인의 Space 를 미리 띄워 두지 않는다.
- 도메인의 QA·고치기·기록이 끝나면 `task.finish({ keep: [] })` 로 닫고 다음 도메인을 연다.

## 고치기

- 도메인의 시나리오를 다 본 뒤 실패를 원인별로 묶어 고친다. 근거는 spec 과 `docs/design/` 설계 문서뿐이다. 근거가 없으면 고치지 않고 QA 파일에 "근거 없음, 사용자 판단 필요"로 적고 다음 실패로 넘어간다.
- 백엔드(`backend/`)만 고친다. 프론트 원인이면 고치지 않고 기록만 한다.
- `git status` 에 내 것이 아닌 변경이 있어도 멈추지 않는다. 그 파일은 건드리지 않고, 커밋할 때 내 파일만 경로로 골라 `git add` 한다. 고칠 파일이 남의 변경과 겹치면 그 실패는 고치지 않고 기록만 한다.
- 실패 하나(QA 파일 하나)마다 이 순서로 한다.
  1. 그 실패를 재현하는 백엔드 시험을 먼저 쓰고, 실패하는 것을 본다.
  2. 근거 문서대로 가장 작게 고친다.
  3. 그 모듈의 시험만 돌려 통과를 본다(`./gradlew :<모듈>:test`).
  4. 커밋 하나로 남긴다(push 는 아직 안 함). 제목은 `fix(<모듈>): QA-<도메인>-NNN <한글 설명>`.
  5. QA 파일의 "해결"에 커밋, 시험 클래스, 고치기 전 실패·고친 뒤 통과를 적는다.
- 도메인의 고치기가 끝나면 전체 시험 없이 몰아서 main 에 push 한다. 전체 시험은 CINX `workbench-ci` Run 이 돌린다. 거기서 깨지면 원인 커밋을 되돌린다.
- 폭주 막기: 고친 것을 되돌린 일이 한 도메인에서 2번이 되거나, 실패와 상관없는 파일을 고쳐야 하거나, 한 도메인에서 20개를 고쳤으면 고치기를 멈추고 남은 실패는 기록만 한다.
- 배포는 사용자가 CINX `devops/workbench` 의 `workbench-ci` 를 Run 해야 반영된다. Run 은 기다리지 않는다. 끝 보고에 "Run 필요"로 적고 끝낸다. 사용자가 Run 한 뒤 다시 부르면 실패했던 시나리오만 다시 본다.

## 기록

- 위치: `docs/qa/<도메인>/`. 형식: `backend/templates/troubleshooting/troubleshooting-TEMPLATE.md`.
- 실패 원인 하나에 파일 하나: `QA-<도메인>-NNN-<증상 한 줄>.md`(번호는 그 폴더 안에서 이어 매긴다). 관련 기능에 spec 번호와 시나리오 번호를 적는다.
- 도메인마다 `요약.md` 하나: 날짜, 대상 커밋, spec 별 통과·실패·판정 불가·확인 불가 수, 실패 파일 목록.
- 실패는 찾는 즉시 QA 파일을 쓰고, spec 하나를 끝낼 때마다 `요약.md` 를 갱신한다. 모아서 나중에 쓰지 않는다.
- QA 파일을 쓰기 전에 백로그에 같은 문제가 있는지 찾는다: `docs/backlog/tasks/<도메인>/`·`docs/backlog/completed/<도메인>/` 에서 spec 번호·증상 낱말로 grep 한다. 있으면 QA 파일 관련 기능에 백로그 번호(예: `CUS-12`)를 적고 `요약.md` 실패 목록에도 함께 적는다. 그 항목이 `tasks/` 의 `결정필요` 이면 고치지 않고 "백로그 <번호> 결정 대기"로 적는다.
- 다시 시작하면 `요약.md` 에 기록이 없는 첫 spec 부터 이어서 본다.
- `요약.md` 와 끝 보고의 수에는 확인 불가·수동도 따로 센다.
- 끝 보고: 도메인, 시나리오 수, 통과·실패·판정 불가·확인 불가·수동 수, 고친 커밋, Run 필요 여부, 사용자 판단 필요 목록.

## 묻지 않고 끝까지

사용자는 자리에 없다(새벽 실행). 도중에 질문하거나 확인을 기다리지 않는다. 판단이 필요한 것은 기록 파일과 끝 보고의 "사용자 판단 필요" 목록에 모으고 다음으로 넘어간다. 아래 "멈추는 경우"만 멈춘다.

## 멈추는 경우

- 로그인이 풀림 → `handOff()` 하고 멈춘다. 갱신 토큰(`WD_RT`)은 로그인부터 12시간이라 그 뒤에는 다시 로그인해야 한다. 멈추기 전에 `요약.md` 를 갱신해 둔다.
- 서버 5xx → 그 시나리오만 실패로 적고 계속한다. 5건이 연달아 나면 서버 장애로 보고 멈춘다.
- ego 오류(브라우저·Space 가 죽음) → 같은 Space 로 한 번 다시 붙어 본다. 안 되면 멈춘다.
- 폭주 막기 조건에 걸림 → 고치기만 멈추고 기록과 끝 보고는 한다.
